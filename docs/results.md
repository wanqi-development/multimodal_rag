## 0. 语料与索引口径

| 项 | 值 |

| 块数 | **1691** |

## 1. 检索层：基线，以及精排到底值多少

来源：§13.3（`rag eval --label baseline` / `--label no-rerank --no-rerank`），22 条检索条目。

| 配置 | recall@8 | MRR | nDCG@8 | top1 |
|---|---|---|---|---|
| 有精排（默认） | **86.4%** | **75.6%** | **78.2%** | **68.2%** |
| 无精排 | 81.8% | 54.7% | 61.1% | 45.5% |
| 差 | +4.6pp | **+20.9pp** | +17.1pp | **+22.7pp** |

**读法**：精排的主要作用不是「多找到几条」（召回只差 4.6pp），而是**把对的那条提到第一**。
这是 `retrieval.rerank.enabled` 默认打开这个取舍的唯一依据。

## 2. 生成层：引用站不站得住

来源：§13.3（`rag eval --label judge-final --judge`），12 条带判据的条目。

| 指标 | 值 |
|---|---|
| 引用准确率（按问题平均，macro） | **90.0%** |
| 引用准确率（按引用条数汇总，micro） | 69.2%（共判 26 条引用） |
| 要点覆盖率 | 94.4% |
| 漏拒 / 误拒 | **0 / 0**（3 条语料外问题全部正确拒答） |
| 判不了（模型输出解析不出来，单列、不算通过） | 0 |

**两种口径要一起看**，macro 与 micro 差 21pp 的原因很具体：一条语料外的问题正确拒答了，
但顺手把查过的 8 条无关材料列成了引用 —— 那 8 条不支持任何论断，把 micro 拖下来。

**引用准确率是自己写的**（`src/rag/eval/metrics.py`）：ragas 的 faithfulness 答的是
「答案有没有超出上下文」，答不了「这个 `[n]` 指的那段原文能不能支撑它所在的那句话」；
两者互补，不是替代（§13.2）。

> 这个指标**修过一次错**：第一版把 `assemble` 发出去的所有编号都算进分母，等于在问
> 「你有没有把材料引用完」，跑出来 76.0%；改成只看答案里**真的引用到**的之后是 90.0%。
> 判据写歪比指标难看危险得多（§13.3）。

## 3. 通道 A/B：两次「用数据否决自己」

### 3.1 BM25 独立通道 —— 删掉（27 题）

来源：§9.1。理由是它与 hybrid 的稀疏腿是**同一份** Milvus 内建 BM25（同索引、同 analyzer、
同一次打分），不可能召回 hybrid 看不到的文档。

| 指标 | 开 bm25 | 关 bm25 |
|---|---|---|
| recall@8 | 87.5% | 87.5% |
| top1 | 62.5% | 62.5% |
| MRR | 71.70% | **71.43%** |
| nDCG@8 | 75.58% | **75.36%** |
| 名次有变化的题 | 2 / 27（一升一降） | — |

单条查询的账本更直观（Kafka 日志保留时间那题）：`hybrid 10→入选 7`、`bm25 10→入选 5`，
两路重叠 4 条 —— **bm25 真正独有的只有 1 条，而那条是跑题的 Flink 块**；
正确答案反倒被从第 7 挤到第 8。代价那边也没占到便宜：多一次 Milvus 往返（142ms）。

### 3.2 Neo4j 图谱通道 —— 默认关、不全量灌图（24 题）

来源：§9.6 / §13.3。同口径对照（含为它加的两条关系类问题）：

| 配置 | recall@8 | MRR | nDCG@8 | top1 |
|---|---|---|---|---|
| `hybrid + bm25`（基线） | 87.5% | 71.7% | 75.6% | 62.5% |
| `hybrid + bm25 + graph` | 87.5% | 71.7% | 75.6% | 62.5% |

**逐题 diff：27 条里名次变化 0 条。** 而且 `--stats` 显示这一路**确实在工作**：
每次召回 10 条候选、耗时约 400ms。加了 `complement_only`（只补别人没找到的块）之后仍然逐字节相同：
召回 10 → 丢重复 5 → 补进 5 条新块 → **入选 0**。

**结论**：问题不在"重复投票稀释名次"，而在图补进来的新块本身不够竞争（根因是图只覆盖 2/5 篇文档，
而这些问题大多是单跳查找）。所以 860 行代码保留、**不进任何默认配置**
（要跑得显式 `--channel hybrid,graph`）。

## 4. 工程侧实测（选型 / 性能 / 排障的依据）

这些数字是"为什么是现在这套实现"的直接依据，也是出问题时一眼能看出毛病在哪的那些。

| 事项 | 实测数字 | 出处 |
|---|---|---|
| PDF 解析选型 | 同一份**数字版** PDF：pymupdf 带标题 **0/20**，OCR 产线 **36/36** → 改成 PDF 统一走 OCR | ADR 23 |
| 精排耗时 × 候选池 | 池子 20 → 重排 26 条 **6.2–7.7s**；池子 10 → 重排 14 条 **4.9s**，正确答案名次与分数一模一样（都 #2 / 0.8113） | §9.3 |
| flashrank vs bge-reranker | flashrank 在中文语料上**分数饱和到 0.9995**、排序退化成 tie-break，还把正确答案挤掉；唯一优势是快 3–4 倍（1.4–1.9s vs 6.2–7.7s）→ 默认用 bge | §9.4 |
| 本机 embedding 吞吐 | 满 1000 字的块只有 **0.32 块/秒**（10 块 31.1s）；真实语料（中位 565 字）整条链路 243 块约 **4 分钟**。估时间用「块数 × 1~3s」 | §16 |
| OCR 产线的转发质量 | 真实负载下 **28% 失败**（34 次 200 / 13 次 500）→ 失败即切云端兜底（按量计费），所以大 PDF 经常走云端 | §7.1 / §16 |
| Milvus 不可达时快速失败 | 加 `ping()` + 5 秒上限之前：`rag ingest` 在写库那一步**空转三十几分钟**（纯 CPU、零 I/O、一行数据没进）；之后：连接被拒 **2.0 秒**返回并给一行中文原因 | §16 |
| 关系库连接成本 | 本机 PG 每次连接约 **0.23s**（比那次查询本身贵两个数量级）→ 文档列表约 0.3s；要再压只能整条链改 async 连接池 | backlog 3.1 |
| MinIO 迁移 | `rag storage migrate`：uploads 52 + stages 117 + assets 137 = **306 个对象**，**7.4s** 搬完（幂等、本地不删） | backlog #12 |
| 语义切分自研 vs `SemanticChunker` | 同语料同模型：自研 6.5s vs 官方 16.3s（慢 2.5 倍），且官方**没有尺寸护栏**（切完最大块 799 字，超阈值近一倍） | ADR 22 |
| xlsx 不用 pandas | 它被本机应用控制策略挡着，且这里用不上它的分析能力 → 改 `openpyxl` 逐行读 | `pyproject.toml` |
| 双版本索引真机探针 | legacy 245 块；复制一份文档的 100 块/已有向量到临时版本化 collection；活动 filter 查回 100，hybrid 命中目标 doc；测试 collection 已清理，legacy 未改 | CHANGELOG 2026-10-23「索引双版本并行」 |

## 5. agent 侧的行为记录（真机）

来源：§11.6。问「Flink 和 Spark 在定位上有什么不同」：

```
list_documents → search_keywords → search_knowledge → get_section
11 步 · 引用 12 条 · 一次图谱都没查 · 答案是对的
```

这条与 §3.2 的 A/B 一致 —— 这份语料上关系信息本来就在正文里，所以图谱通道没必要默认开。
同时它是「工具面收敛到 4 个」这个决定的现场证据：模型自己选了最省事的那条路，
没被多余的工具带偏。

## 6. 边界（这些数字不能拿来宣称什么）

* 黄金集 **30 行**、语料 5 篇级别 —— 做 A/B 对照与回归够用，**不代表绝对水平**；
* 没有与公开 benchmark（MTEB / 业界 RAG 榜单之类）做过对比，也没有跨模型横向评测；
* 生成侧 macro / micro 两个口径都在，**micro 只有 69.2%** 那条短板是真实存在的
  （拒答时列了无关引用，两条改法见 §13.3，都还没做）；
* 一次评测要真 Milvus + 本地模型；带 `--judge` 的部分按量计费（每个问题一次模型调用）。

## 7. 复现

```bash
# 检索层（不花钱：本地 embedding + 本地精排）
rag eval --label baseline --top-k 8
rag eval --label no-rerank --no-rerank
rag eval --label ab-with-graph --channel hybrid,graph      # 图谱那一路要先 rag graph build

# 生成侧（花钱：带 judge 的部分每个问题一次模型调用）
rag eval --label judge-final --judge
rag eval --label judge-ragas --judge --ragas               # 再加 ragas 的 faithfulness
```

报告落在 `eval/reports/<label>-<时间戳>.json|md`；`--label` 是 A/B 对比用的前缀，
同一批问题换个标签再跑一次即可并排看。
