# Milvus 字段设计与增量更新（设计稿）

> 状态：**设计稿，未实现**。评审通过后再动代码。
>
> 解决的问题：① 图片路径没有落库、追溯不了；② 块不知道自己属于哪个标题、在第几页第几行；
> ③ 源文件变了只能全量重灌。第三件事代价最大 —— 解析（OCR）与 embedding 都在变更检测**之前**，
> 所以检测必须发生在解析之前才省得下来。

## 1. 现状诊断

灌库后真实的一行长这样（`rag_dev_qwen3`，202 行）：

```
chunk_id   : be6840371b6aab15:0000
doc_id     : be6840371b6aab15
chunk_index: 0
source_uri : 从Agent到手撕OpenClaw的企业实战.docx
metadata   : {"source_uri":"从Agent…docx", "parser":"docx", "image_count":45,
              "h1":"从Agent到手撕OpenClaw的企业实战"}
text       : "# 从Agent到手撕OpenClaw的企业实战 ⏎ ![image](asset:be6840371b6aab15/img001.png)"
```

### 现有四个字段是什么

| 字段 | 实际内容 | 可读性 |
|---|---|---|
| `chunk_id` | `{doc_id}:{序号:04d}`，主键 | 半可读 |
| `doc_id` | **`sha1(语料相对路径)[:16]`** —— 路径哈希，不含内容 | **不可读** |
| `chunk_index` | 块在**本文档内**的序号（0 起，每份文档重置） | 可读；要配 `doc_id` 才唯一 |
| `source_uri` | 语料根下的**相对路径** | 可读，真正用来追溯的是它 |

`doc_id` 用路径哈希是有意的（ADR 15）：路径哈希让重复 ingest 原地覆盖；内容哈希会让改一个字就换
id、旧块全成孤儿。

### 六处问题

| # | 问题 | 后果 |
|---|---|---|
| 1 | **图片路径只存在于 `text` 里** | 找「哪些块带图」只能 `text like "%asset:%"`；块里有哪几张图、图叫什么，结构化字段里一概没有 |
| 2 | **页码、行号完全没有** | 引用里最常被问「第几页」答不上来。OCR 那条路本来知道页号，在拼正文时被丢掉了 |
| 3 | 标题层级埋在 `metadata` JSON 里（`h1`/`h2`/`h3`） | 能过滤但不如顶层字段方便；且没有「标题路径」这个整体概念 |
| 4 | `metadata.image_count` 是**文档级**的 | 对追溯没用 —— 它说「这份文档有 45 张图」，不说「这块里有哪张」 |
| 5 | `source_uri` 存了两份（顶层字段 + metadata） | 冗余，容易改一处漏一处 |
| 6 | **没有任何内容指纹** | 无法判断「这份文件变了没有」，于是每次都全量重算 |

## 2. 字段设计

### 2.1 块表（`rag_<profile>_<embedding指纹>`，如 `rag_dev_qwen3`）

> 原则沿用 `schema.py` 开头那条：**该过滤的放显式字段，只是留痕的才进 JSON**。
> 字段全部显式声明（`enable_dynamic_field=False`）。

| 字段 | 类型 | 谁填 | 示例 / 说明 |
|---|---|---|---|
| `chunk_id` | VARCHAR(64) **主键** | `make_chunk` | `be6840371b6aab15:0000` |
| `doc_id` | VARCHAR(64) | `doc_id_for` | `sha1(相对路径)[:16]` |
| `chunk_index` | INT64 | `make_chunk` | 文档内序号，0 起 |
| `source_uri` | VARCHAR(1024) | `rel_uri` | 相对语料根的路径 |
| **`doc_type`** | VARCHAR(16) | loader | `docx` / `html` / `pdf` / `xlsx` / `md` / `image` |
| **`modality`** | VARCHAR(16) | chunker | `text` / `image` / `table` |
| **`heading_path`** | VARCHAR(1024) | chunker | `第一章、概念 -> 1、什么是Agent？`；无标题时空串 |
| **`heading_numbers`** | VARCHAR(64) | chunker | **位置派生**的层级编号 `1-2-3`；无标题时空串。见 §2.5 |
| **`page`** | INT64 | locate | 1 起；**0 = 该格式没有页的概念** |
| **`line`** | INT64 | locate | 1 起；**0 = 没有行的概念**。含义随 `doc_type` 变，见 §2.3 |
| **`assets`** | ARRAY\<VARCHAR\>(64) | loader | 本块引用的资产 uri；空数组 = 无图 |
| **`content_hash`** | VARCHAR(16) | 切块后 | `sha1(text)[:16]`，去重用 |
| `metadata` | JSON | 各层 | **收敛**：只留没进上面显式字段的东西（如 `chunk_strategy`、`scanned_pages`）。**删掉 `h1`/`h2`/`h3` 与重复的 `source_uri`** |
| `text` | VARCHAR(8192) `analyzer=chinese` | chunker | 正文；BM25 的 sparse 由服务端从它生成 |
| `dense` | FLOAT_VECTOR(dim) | embedder | Qwen3-Embedding，1024 |
| `sparse` | SPARSE_FLOAT_VECTOR | Milvus BM25 function | **不写不读** |

几个取舍：

- **`assets` 用 `ARRAY<VARCHAR>` 而不是 JSON**：类型化、能声明容量、可用 `array_contains` 过滤 ——
  与「显式声明」的立场一致。容量定 64：一个块 ≤1000 字符，一个图片标记约 40 字符，理论上最多
  约 25 个，64 有充分余量。**超了就在写入时当场报错**（像现在 `text` 超长那样），不静默截断。
- **`heading_path` 是标题层级唯一的来源**，不再另存 `h1/h2/h3`。想筛「某一节里的块」用前缀匹配
  （`heading_path like "第一章、概念 ->%"`）就够。
- **`content_hash` 与 `doc_id` 是两回事**：前者是**块内容**哈希（去重、查重），后者是**文档路径**
  哈希（幂等覆盖）。网页里同一段导航重复出现时，前者能识别出来。

### 2.2 文档注册表（新 collection，`rag_<profile>_docs`）

每份**文档**一行，而不是每块一行 —— 这是增量更新的依据，也是「这份文件上次灌的是什么」的答案。

| 字段 | 类型 | 说明 |
|---|---|---|
| `doc_id` | VARCHAR(64) **主键** | 与块表的 `doc_id` 一致 |
| `source_uri` | VARCHAR(1024) | 相对路径 |
| `content_hash` | VARCHAR(16) | **文件字节**的 `sha1[:16]` —— 变更检测的钥匙 |
| `chunk_count` | INT64 | 上次灌进去多少块 |
| `ingested_at` | INT64 | Unix 时间戳 |
| `pipeline_version` | VARCHAR(64) | 切分策略 + 清洗规则 + embedding 模型的指纹，见 §4.3 |

**为什么单独一个 collection，而不是塞进每个块的 metadata**：注册表是 O(文档数) 的，做 diff 时只读它；
塞进块里就得扫全部块才能列出一份清单。

⚠️ **它必须带一个向量字段** —— 建的时候实测撞到两条 Milvus 硬约束：

```
① code=1100 schema does not contain vector field      —— 只有标量字段的 collection 建不了
② code=1100 invalid dimension: 1. should be in range 2 ~ 32768
```

所以注册表带一个 **2 维的 `placeholder`**（FLAT/COSINE 索引）。它**不参与任何检索**，
纯粹为了能建表，代价是每行 8 字节。写入时固定 `[0.0, 0.0]`。

### 2.3 `page` / `line` 在每种格式下意味着什么

**这是整份设计里最需要说清楚的一点：这两种信息各格式能拿到的程度差得很远。**

| 来源 | `page` | `line` | `heading_path` | 说明 |
|---|---|---|---|---|
| PDF（OCR 产线） | ✅ 产线按页返回 | ✅ **页内行号** | ✅ `relevelTitles` 重建的 `#` | 最完整的一条路 |
| PDF（`parser: pymupdf` 降级） | ✅ | ✅ 页内行号 | ❌ 纯文本没有标题 | 有损路径 |
| docx | ❌ 无页概念 → 0 | ⚠️ **段落序号** | ✅ 样式或字号推断 | 「第 N 段」不是「第 N 行」，但足以定位 |
| html | ❌ → 0 | ❌ → 0 | ✅ `<h1..h6>` | **源码行号没有意义**（换行与压缩取决于保存方式） |
| xlsx | ❌ → 0 | ✅ **表内行号** | ✅ 表名 | 「客户清单 第 5 行」是天然定位 |
| 独立图片 | ❌ → 0 | ❌ → 0 | ❌ | 只有它自己 |

所以 `line` 的语义**随 `doc_type` 变**，引用展示时按 `doc_type` 渲染成人话
（`第 12 页第 3 行` / `客户清单 第 5 行` / `第 87 段`）。**不假装它是统一的东西。**

### 2.4 正文（要被 embedding 的那段文本）怎么组成

**标题不在正文里。** 切分时先把标题剥掉（`strip_headers=True`），切完再把它**贴到开头**：

```
正文块：   <标题1> -> <标题2>
           （空行）
           <内容>

图片块：   <标题1> -> <标题2>
           （空行）
           <图片描述>
           <图片地址>
```

这样正文是干净的内容本身，标题以一个**结构化的题头**出现 —— 读到这一块的人（或模型）
先知道它在哪一节里。剥离再贴回、而不是让它留在原地，也让正文与标题的边界明确、展示时能分开渲染。

#### 位置是有实测数据的：开头 vs 末尾

Qwen3-Embedding-0.6B 是 **last-token 池化**（模型的 `1_Pooling/config.json`：
`pooling_mode_lasttoken: true`），末位内容对向量影响最大，所以贴哪一头不是小事。
拿 8 段同节真实正文（平均 723 字）实测平均两两余弦：

| 布局 | 平均两两余弦 | 说明 |
|---|---|---|
| 标题在末尾 | 0.6830 | 区分度最好 |
| **标题在开头（当前选择）** | **0.8166** | 同节块最相似 |
| 不带标题（纯内容） | 0.5899 | 最区分，但也丢了章节信息 |

**这是一个有意做的取舍**：放开头读起来自然（先看到所属章节），但**同节块的向量会更相似、
区分度下降**（0.68 → 0.82）。

两点补充：

1. 无论贴哪一头，**带标题都会让同节块更相似**（0.59 → 0.68/0.82）—— 这是为「标题词进向量、
   能命中章节类查询」付的钱。§4.6 那套「标题单独成字段 + 让大模型生成过滤条件」正是把它补回来。
2. 想换回末尾是**一行的事**（`chunkers/base.py::with_heading_path`），上面的数据留着备查。

### 2.5 `heading_numbers`：按作者编号重建层级（2026-09-30 修正）

**这一节的初版判断是错的，被真实数据推翻了。** 初版写的是「位置派生，不解析作者编号」：
与作者怎么写编号无关、永远连续可比较。问题在于位置派生的前提是**层级本身可靠** ——
而这个前提在这些语料上不成立：OCR 产线的 `relevelTitles` 会把章、节、列表项标成同一级。

灌完三篇 PDF 后实测（`heading_numbers` 不从 1 开始的块）：**第一章 65/68、第二章 23/45、
Kafka 243/1007**；典型样本是 `APP移动端数据 -> 6. 实时报表分析` 编号 `4-17`（对应书里的
`1.5`），以及 `MyFlinkCode FlinkScalaCode` 这种**只有一层、完全不带父级**的路径。
位置派生在这里是纯粹的数字，用户问「第 4 章第 17 节」根本对不上。

现在的规则（实现见 `ingest/headings.py`）：**按作者编号重建树**。

```
2.1 / 2.2.1 这类多段编号 → 段数就是层级，最可靠的一档
2. APIS 这类单段编号     → 只有在「后面跟着它的小节（2.x）」且「编号大于已确认的最大章号」
                            时才算章；否则是列表项（1. 打开IDEA… 就是列表项）
没有编号的标题           → 挂到最近一个「结构节点」之下，路径从根到现在完整拼出来
```

三条判据都是被真实数据逼出来的：只看「编号接在后面」会把列表步骤 `3. 打开Structure`
当成第 3 章（那份教材的步骤正好是 1./2./3./4./5.）；只看「有下级」会把 `2. 在IntelliJ…`
当成第 2 章（因为文档后面确实有 2.3）。

实测效果（第二章 PDF，47 块）：**不从根开始的块 44 → 0**，编号从 `7-2`/`12-1` 变成
`2-2-1`/`2-3`，与书中编号一一对应。

⚠️ **前缀匹配要带分隔符**：`like "1-2%"` 会误匹配 `1-20-1`。所以过滤要用
`heading_numbers == "1-2" or heading_numbers like "1-2-%"` —— 带尾分隔符才是「本节及其子节」的精确含义。

## 3. 位置信息怎么拿到（技术难点）

现在的链路是「纯文本」的：loader 把多页拼成一份 `Document.text`，页边界当场丢掉；chunker 返回
字符串、不报告偏移。所以页码/行号无处附着。

### 3.1 三步走

第一步，**loader 产出位置映射**：新增契约字段

```python
class Position(BaseModel):
    offset: int   # 在 Document.text 里的字符偏移
    page: int     # 1 起；0 = 无页概念
    line: int     # 1 起；0 = 无行概念

class Document(BaseModel):
    ...
    positions: list[Position] = []
```

按 offset 升序、**稀疏**（只在页码或行号变化处打点）。OCR 那条路最好办：产线**本来就按页返回**，
`pages_to_text()` 在拼页时记下每页的起始偏移即可；行号在页内数 `\n`。

第二步，**切完块后把块映射回偏移 —— 不动 chunker**。切块器（含 LangChain 的）都只
返回字符串，让它们带上偏移要改一大圈。改成切完之后逐个定位：

```python
cursor = 0
for chunk in chunks:
    # ⚠️ 不能直接 find(chunk.text) —— 见下面的坑
    at = squashed.find(needle, cursor)   # 两边都去掉空白再匹配
    cursor = at + 1
```

单调游标能处理**重叠**（`overlap` 会让同一段文字出现在相邻两块里）：每次从上一块的起点往后找，
不会匹配到更早的那一份。找不到时（理论上不该发生）记为 0 并在日志里出声，**不静默**。

> ⚠️ **坑（实测）**：`MarkdownHeaderTextSplitter` **会改写空白** —— 连续空行、行尾空格、
> CRLF 都被它归一化，所以切出来的块正文**不是原文的逐字子串**，直接 `find` 会大面积落空
> （第一版只有一半的块定位上，失败集中在空白多的前半段）。
>
> 修法：定位前把 `doc.text` 与块正文都**去掉所有空白**再匹配，同时记一张
> 「压缩后字符 → 原文偏移」的映射表，拿到匹配位置后换回原偏移。位置仍然精确，
> 且对任何空白差异免疫。实现在 `ingest/__init__.py::_squashed`。

第三步，**偏移 → (page, line)**：对 `positions` 二分，取最后一个 `offset <= 目标` 的点。

### 3.2 图片的位置就是标记的位置

图片不需要额外机制 —— 正文里的 `![image](asset:…)` **标记本身就落在原位**。对标记做一次
`doc.text.find(marker)` 就得到它的偏移，于是同一套 `page`/`line` 直接可用；标题路径则继承
**所在块**的那一份（header 切分保证一个块不跨小节）。

这也意味着：**图片描述块可以直接复用这组字段**，与它描述的那张图对齐。

## 4. 增量更新

### 4.1 三态 diff

扫描语料目录时**只读文件、不解析**，逐个算 `content_hash`：

- 注册表里没有 → **新增**：解析 → 切分 → embedding → 写块 + 写注册行
- 有，且 hash 相同 → **跳过**（连解析都不做）
- 有，但 hash 不同 → **变更**：先按 `doc_id` 删旧块，再走新增流程
- 注册表里有、语料里**找不到文件** → **删除**：删块 + 删注册行

第四态是现在完全没有处理的：语料里删掉一份文件，库里的块会永远留着。

### 4.2 为什么指纹用「文件字节哈希」

| 候选 | 评价 |
|---|---|
| `mtime` | ❌ 备份/同步工具会改它，而内容没变 |
| `size` | ❌ 改名、换字都会漏 |
| **文件字节 `sha1`** | ✅ **最便宜**：只读文件、不用先解析 —— 这正是关键，检测必须便宜到能对全语料跑一遍 |
| 解析后正文哈希 | ✅ 可作为**第二层**：文件哈希变了但正文哈希没变（比如只改了作者信息）→ 只更新注册信息，不重灌。解析的钱已经花了，这层几乎白捡 |

代价：**重新保存一次（哪怕只改了元数据）就会触发重解析**。方向**选宁可多算** —— 重解析一份
docx 几十秒可以接受，而误判「没变」导致库里是旧内容，是不可接受的错误。

### 4.3 `pipeline_version`：内容没变但结果该变

改了切分策略、改了清洗规则、换了 embedding 模型 —— 这时文件哈希完全相同，增量会跳过它，
库里就留着**用旧规则切出来的块**。所以注册表要存一个指纹：

```
pipeline_version = sha1(
    切分策略 + size + overlap + semantic 参数
    + 清洗规则版本 + OCR 的 restructure/merge/relevel 开关
    + embedding 模型名 + dim
    + 图片描述开关（关着只记 False；开了才带 VL 模型名 / 提示词版本 / max_images）
)[:16]
```

最后那一项是 2026-09-30 补的：**打开 `ingest.images.describe` 时文件一个字节都没变**，
不写进指纹的话增量会把所有文件跳过，结果一张图都没描述、而库里「看起来是新的」。
关着时只记 `False` —— 否则改一下 VL 模型名就会白白重灌整个语料。

不匹配就强制重灌那一份。这是 collection 名带 embedding 指纹那套思路的延伸 ——
**collection 名管「向量空间变了」，`pipeline_version` 管「切法变了」。**

### 4.4 图片描述要单独缓存（2026-09-30 已实现）

图片描述是整条链路里最贵的一步（每张一次 VLM 调用，按量计费）。而**改一段文字不该让 45 张图
全部重跑**。所以描述要以**图片内容哈希**为键缓存：

```
`ingest/images.py::_DescriptionCache` 落一个 json（`ingest.images.cache_path`，默认
`./data/cache/image_descriptions.json`）：

```
{ "<sha1(图片字节)[:16]>:<模型名@提示词版本>": { "text": …, "at": <unix 秒> } }
```

键里带**模型名与提示词版本**：换了模型、或改了提示词，旧描述就不该再被复用。
提示词版本在 `config/schema.py::VISION_PROMPT_VERSION`（同一个常量也进 `pipeline_version`，
所以「改了提示词」会连重灌一起触发）。缓存坏了当作空缓存重来 —— 它只是省钱的手段，不是数据。

**没走「资产文件名带内容哈希」那条路**：那要改命名规则（现在按页与序号 `p0003_01.jpg`，
同一份文档重灌原地覆盖），而 `doc_id + asset_uri` 的稳定性对追溯更重要。缓存单独放一个 json，
与资产的命名解耦。

**这一条必须和「图片 → VLM 描述」一起做**，否则每次重灌都要重烧一遍钱：改一段正文会让
整份文档重灌（§4.1），描述缓存不命中就是几十张图重问一遍 VLM。

### 4.5 CLI 形态（2026-09-30 已实现）

```bash
rag ingest ./data/docs              # 默认增量：新增 / 变更 / 跳过 / 删除
rag ingest ./data/docs --full       # 强制全量重灌
rag ingest ./data/docs --dry-run    # 只打印将要做什么，不写
```

`--dry-run` 的实际输出：

```
collection=rag_dev_qwen3_v2  uri=http://192.168.x.x:19530
PDF 解析=ocr  OCR=http://127.0.0.1:8080
扫描 6 篇 -> 新增 6 / 变更 0 / 跳过 0 / 删除 0
  + Get Started with Kafka _ Confluent Documentation.html
  …
--dry-run：什么都没写。
```

（变更的以青色 `~` 列出；删除的以 `-` 加 doc_id 列出。）

实现上的五个注意点：

1. **每个 path 参数各算语料根**，但同一次发现里必须沿用同一个根 —— `doc_id` 与
   `source_uri` 都相对它算，换成各文件的父目录会让子目录里的文件算出另一个 doc_id，
   注册表就对不上了。为此新增 `ingest.prepare_paths(paths, root, ...)`：
   只处理指定的这一批文件，但**用同一个根**；`prepare()` 成了它的特例。
2. **删除检测只在目录源上做** —— 单文件源看不出「别的文件没了」。
3. **删的顺序**：先删块、再删注册行。反过来中途失败会留下「有块没注册」的孤儿；
   这样只会留下「注册在、块没了」，下次跑会重做 —— 是安全的方向。
4. **解析失败或正文为空的文件不注册**：注册了就会被当成「已入库」、下次直接跳过，
   那等于把一次失败永久固化下来。
5. **`--dry-run` 连 `ensure_ready()` 都不调**，只读一次注册表 —— 它不该改库的结构。

### 4.6 「第三章第二节讲什么」这类查询怎么走

**纯语义检索答不了这个。** 用户问的是**结构位置**，而向量空间里没有「第三章第二节」这个概念 ——
语料里对应的文字可能是「1.2 核心概念」，字面上完全对不上。所以要**让大模型把问题翻成过滤条件**：

```
用户问："第三章第二节讲了什么"
   ↓  plan 节点（大模型，M3 的 QueryGraph）
过滤条件：heading_numbers == "3-2" or heading_numbers like "3-2-%"
语义部分：用问题本身再检索一遍（拿语义相关性）
   ↓
两者结合：过滤缩小范围 + 语义排序
```

两个字段各有分工：

| 字段 | 谁用 | 怎么用 |
|---|---|---|
| `heading_path` | 展示 + 大模型 | 大模型看到真实标题文字，才能把「第三章第二节」对上号；引用里也显示它 |
| `heading_numbers` | 过滤 | 编号是位置派生的、连续可比，适合生成精确的过滤表达式 |

**必须有的回退**：大模型可能生成一个不存在的编号（文档只有两章，它生成了 `3-2`），
或者文档的编号与用户数的章号不一致（中间有个没编号的 h1）。这时过滤会返回 0 条 ——
**要能退回去「只用语义检索」重来一次**。M3 的 QueryGraph 本来就有 grade 自我纠错循环，
正好接得上：**过滤后 0 条 → 去掉过滤重试**，并把这次失败记下来。

## 6. 已知弱点 / 不做的事

| 项 | 说明 |
|---|---|
| 注册表与块表**不是原子更新** | 删块 + 删注册行分两步，中途失败会留下不一致。靠 `doc_id` 主键 + 全流程幂等兜住：下次跑会重做。要在代码里写明 |
| **不做块级 diff** | 块会移位，`chunk_id` 是 `doc_id:序号`，增删一段就大面积错位。文档级重切是唯一能保证一致的做法 |
| html 拿不到行号 | 保存方式不同、源码换行无意义，硬做是假精度 |
| `line` 语义随格式变 | 有意为之（§2.3），引用展示按 `doc_type` 渲染；**不假装统一** |
| 单调 find 可能失配 | 理论上块文本一定出现在正文里；真失配时记为 0 并出声，不静默填一个假位置 |
| `assets` 容量 64 | 超了在写入时报错。若将来块尺寸放大，这个上限要跟着调 |
| **标题存了两份**（正文末尾一份、`heading_path` 字段一份） | 有意的：正文那份是为了**进向量**（标题词可被检索到），字段那份是为了**过滤与展示**。代价是每块多背几十字符 |
| **`strip_headers` 要改成 True** | 现在的实现是把标题留在正文里。改成「剥离 + 末尾追加」会**改变所有块的正文与向量** —— 所以这一步和字段改动是同一批，一起重建 |
| 大模型生成的编号可能不存在 | 过滤返回 0 条时要能回退到纯语义检索，不能就此报「查不到」（见 §4.6） |
